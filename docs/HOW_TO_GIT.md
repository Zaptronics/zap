# How to Git Zap

This is the practical Git/GitHub workflow for the **Zap** repository. It is intentionally short and project-specific rather than a general Git tutorial.

## The normal everyday workflow

Before starting work, make sure `main` is current:

```powershell
git status
git pull --rebase origin main
```

After making changes:

```powershell
git status
git diff
go test ./...
```

Stage and commit them:

```powershell
git add -A
git commit -m "Short description of the change"
```

Then push:

```powershell
git push origin main
```

That push starts the normal GitHub **CI** workflow on Windows, Linux, and macOS. CI runs the tests and proves Zap builds, but the executables made by CI are temporary and are discarded when the runner finishes.

For an ordinary commit, there is therefore **no downloadable Zap binary** produced by GitHub.

## Making a Zap release

Release binaries are made by the separate GitHub **Release** workflow. It runs only when a tag beginning with `v` is pushed, for example `v0.6.0`.

First make sure the release commit is clean, tested, and pushed:

```powershell
git status
git pull --rebase origin main
go test ./...
git push origin main
```

Create an annotated version tag:

```powershell
git tag -a v0.6.0 -m "Zap 0.6.0"
```

Then push the tag:

```powershell
git push origin v0.6.0
```

GitHub Actions then runs `.github/workflows/release.yml`. If it succeeds, GitHub creates a new entry under **Releases** and attaches:

```text
zap_windows_amd64.zip
zap_windows_arm64.zip
zap_darwin_universal.zip
zap_linux_amd64.tar.gz
zap_linux_arm64.tar.gz
zap_X.Y.Z_linux_amd64.deb
zap_X.Y.Z_linux_arm64.deb
zap_X.Y.Z_linux_amd64.rpm
zap_X.Y.Z_linux_arm64.rpm
SHA256SUMS.txt
```

The workflow also injects the tag version into the Zap executable, so a release tag should represent the exact source you want to publish. When signing/publishing is configured, the same release can also update the Zaptronics Homebrew tap and submit a WinGet package update. See `RELEASE_DISTRIBUTION.md` for the one-time publishing setup and `CODE_SIGNING.md` for signing credentials.

### Where to find the result

- **Actions** shows whether CI or the Release workflow succeeded.
- **Releases** contains the permanent downloadable release binaries.
- A normal commit does **not** currently upload a downloadable build artifact.

GitHub Releases themselves need no extra destination configuration. Package-manager publishing does require one-time setup: a Zaptronics Homebrew tap repository/token, an accepted first WinGet manifest, and the signing credentials described in `RELEASE_DISTRIBUTION.md` and `CODE_SIGNING.md`.

## Applying one of our patches

Always check a patch before applying it:

```powershell
git apply --check .\some_change.patch
```

If that succeeds:

```powershell
git apply .\some_change.patch
git status
git diff
```

Then test, commit, and push normally.

Patches for Zap should be relative to the **Zap repository root**. Generated files should normally be regenerated by their owning tool rather than patched by hand.

## Useful checks

See what changed:

```powershell
git status
git diff
```

See recent commits:

```powershell
git log -10 --oneline --decorate
```

See tags:

```powershell
git tag --sort=-version:refname
```

See which branch and remote are in use:

```powershell
git branch --show-current
git remote -v
```

## If a push is rejected because `main` moved

Bring the remote commits in without creating an unnecessary merge commit:

```powershell
git pull --rebase origin main
```

If that succeeds:

```powershell
git push origin main
```

If the rebase has conflicts, fix the files, then:

```powershell
git add <fixed-files>
git rebase --continue
```

To abandon the rebase and return to the state from before it began:

```powershell
git rebase --abort
```

## Undoing things safely

Discard an **unstaged** change to one file:

```powershell
git restore path\to\file
```

Unstage a file but keep its edits:

```powershell
git restore --staged path\to\file
```

Change the most recent commit **before it has been pushed**:

```powershell
git add -A
git commit --amend
```

If a bad commit has already been pushed/shared, prefer creating a reversing commit rather than rewriting shared history:

```powershell
git revert <commit-hash>
git push origin main
```

## If a release tag is wrong

If the tag has **not** been pushed yet, simply delete it and recreate it:

```powershell
git tag -d v0.6.0
```

Once a release tag has been pushed and published, prefer fixing the problem and releasing a new patch version such as `v0.6.1` rather than rewriting a published release.

## The short version

For normal work:

```powershell
git pull --rebase origin main
# edit
go test ./...
git add -A
git commit -m "Describe change"
git push origin main
```

For a release after the release commit is already pushed:

```powershell
git tag -a vX.Y.Z -m "Zap X.Y.Z"
git push origin vX.Y.Z
```

Then check **GitHub → Actions**. When the Release workflow finishes, the permanent binaries/packages are under **GitHub → Releases**; if package-manager publishing is enabled, the workflow also updates Homebrew and WinGet.
