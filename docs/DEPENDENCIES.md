# Dependency lifecycle

Zap separates dependency **intent** from dependency **resolution**:

- `zap.yml` is edited by people and declares sources, version constraints, local
  paths, and the direct components the application wants.
- `zap.lock` is generated by Zap and records the exact dependency graph that was
  resolved, including immutable Git commits and package-manifest hashes.
- `deps/` is the materialised working copy used by CMake/Zephyr.

Commit both `zap.yml` and `zap.lock` to source control. Do not hand-edit
`zap.lock`.

## Adding and removing dependencies

Until a package registry exists, a new dependency needs an explicit source:

```text
zap add zapee --git https://github.com/Zaptronics/zap-ee.git --version ^0.5.0
zap add mylib --path ../mylib
zap remove mylib
```

For Git dependencies, omitting `--version` asks Zap to find the newest stable
`x.y.z` tag and write a compatible-major (`^`) constraint.

Select package CMake targets with:

```text
zap component add zapee zap::ztm_pwm
zap component remove zapee zap::ztm_pwm
```

The old `zap add <dependency> <component>` and
`zap remove <dependency> <component>` spellings remain as deprecated
compatibility aliases for now.

## Version constraints

Git dependencies support:

| Form | Meaning |
| --- | --- |
| `1.2.3` or `v1.2.3` | exactly version 1.2.3 |
| `^1.2.3` | `>=1.2.3 <2.0.0` |
| `^0.5.1` | `>=0.5.1 <0.6.0` |
| `~1.2.3` | `>=1.2.3 <1.3.0` |
| `>=1.2.0 <2.0.0` | explicit range |
| `tag:v1.2.3` | explicit Git tag |
| `ref:develop` | Git branch/ref |
| `commit:<40-char-sha>` | exact immutable Git commit |

Legacy bare refs such as `main` are still accepted; new manifests should use
`ref:main` so intent is unambiguous.

Zap v1 resolver currently recognises stable three-component semantic-version
tags (`x.y.z`, optionally prefixed with `v`). Pre-release/build metadata is not
part of this resolver version.

## `zap.lock`

For example, this intent:

```yaml
schema: 5

dependencies:
  zapee:
    type: git
    uri: https://github.com/Zaptronics/zap-ee.git
    version: ^0.5.0
    components:
      - zap::ztm_pwm
```

might resolve to:

```yaml
# Zap dependency lockfile. Commit this file. DO NOT EDIT BY HAND.
schema: 1

dependencies:
  zapee:
    type: git
    uri: https://github.com/Zaptronics/zap-ee.git
    direct: true
    root_requested: ^0.5.0
    requested:
      - ^0.5.0
    resolved: v0.5.3
    commit: 0123456789abcdef0123456789abcdef01234567
    manifest_sha256: aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
    root_components:
      - zap::ztm_pwm
    components:
      - zap::ztm_pwm
    parents:
      - root
```

`zap sync` preserves a compatible existing lock. It does **not** silently move
versions just because a newer matching tag appeared remotely.

Use `zap update` when you deliberately want the lock to move forward:

```text
zap update               # all packages, within zap.yml constraints
zap update zapee         # one direct or transitive package
```

Changing the declared constraint is separate:

```text
zap version zapee ^0.6.0
```

## Transitive package dependencies

`zap-package.yml` schema 2 lets a package depend on another package. Zap resolves
the complete graph, materialises transitives, and records them in `zap.lock`.

For example:

```yaml
schema: 2
package:
  name: MotorControl

dependencies:
  transport:
    type: git
    uri: https://github.com/example/transport.git
    version: ^1.4.0
    components:
      - transport::spi

components:
  motor::core:
    kind: module
```

A package-level dependency is part of that package's dependency graph. The
package remains responsible for linking its own CMake targets to dependency
targets; Zap makes sure the required dependency source/targets exist first.

Transitive Git dependencies may use Git sources and constraints. A transitive
`path` dependency is allowed only when its parent is itself a local `path`
package, where the path can be resolved relative to that package. Transitive URL
archives are not supported in resolver v1.

## Conflict resolution

Resolver v1 chooses **one version of a package name for the whole graph**. All
constraints on that name must have a common solution.

If package A requires `B ^1.0.0` and package C requires `B ^2.0.0`, Zap fails
rather than silently installing two incompatible copies:

```text
dependency conflict: b: no stable release satisfies all version constraints
  a -> b requires ^1.0.0
  c -> b requires ^2.0.0
```

Likewise, requirements with the same dependency name must agree on source type
and URI. Side-by-side major versions are intentionally not part of resolver v1.

## Inspecting the graph

```text
zap tree
zap tree --why transport
zap outdated
zap list
zap status
```

`zap tree` shows the resolved parent/child graph. `--why` prints every path from
the application root to one dependency.

`zap outdated` does not modify anything. For semantic-version dependencies it
shows the newest release allowed by the declared constraints and the newest
stable release overall. For a branch/ref lock it reports when the remote ref has
advanced.

## Reproducibility and verification

`zap verify` checks that:

- `zap.lock` still matches direct intent in `zap.yml`;
- managed Git dependency origins and `HEAD` commits match the lock;
- managed Git worktrees report clean according to Git;
- package manifests read from locked Git objects match their recorded digest;
- URL declarations contain a valid SHA-256 hash (content checking is delegated to CMake); and
- release tags still resolve to their locked commits when online.

Use:

```text
zap verify --offline
```

to skip remote lookups while retaining local lock/check-out verification.

Missing managed Git checkouts are errors online and offline. URL dependencies are
rejected by offline verification because Zap has no URL content verifier. Git-hidden
edits and ignored files can evade current checkout checks. Independent source
hashes and a verified cache are planned, not implemented; see [SECURITY.md](../SECURITY.md).

Local `path` dependencies are intentionally mutable. `zap sync` therefore
re-resolves their package manifests each time and refreshes the lock's manifest
digest.

## Updating older projects

Older Zap project schemas stored an immutable `commit:` beside `version:` in
`zap.yml`. The first `zap sync` with resolver v1 migrates that state:

1. the existing locked commit seeds `zap.lock`;
2. `zap.yml` is rewritten to schema 5 without `commit:`; and
3. subsequent builds use `zap.lock` as the immutable resolution record.

The migration preserves the existing locked Git commit rather than upgrading it.
